# ESP32-C6 collector-path verification — 2026-10-12

**MEASURED: PASS**, using a physical ESP32-C6 and the 0.4.0 CLI on Windows
x86-64 (Rust 1.97.1). This verifies data transport and downstream processing;
it does not establish sensing accuracy, event correctness against ground truth,
long-duration performance, or direct device JSON serial compatibility.

## Device and scope

A serial boot log identified ESP32-C6 revision 0.2, 160 MHz, running
`esp32-csi-node` firmware **0.7.0**, compiled 2026-06-02 11:10:30, with ELF
SHA-256 prefix `ee4c49c95`. The ROM banner was `esp32c6-20220919`. The firmware's
ESP-IDF version string was `-128-NOTFOUND`, so an exact IDF release is unknown.
The board was already configured to send CSI over UDP. No firmware was flashed
and no network configuration was changed. A normal reset captured its boot log.

The device emits RuView ADR-018 binary packets, not the adapter's JSON contract.
The measured path was:

```text
physical ESP32-C6 -> binary UDP -> bounded Python collector
                 -> loopback JSON UDP -> Rust adapter -> validated .rvcsi
```

The collector validates the 20-byte little-endian header, raw-CSI magic,
configured node, single antenna, subcarrier count, channel frequency and exact
payload length. Other packet types are excluded. Header bytes 12–15 contain a
**sequence number**, not a timestamp. JSON `ts_ns` uses host receive time in
nanoseconds. The collector preserves the firmware's signed imaginary/real
bytes. It does not infer `first_word_invalid`; this wire format does not carry
that boolean. Hardware evidence therefore does not qualify first-word handling
(covered separately by synthetic regression tests).

## Observations

- 128 live raw-CSI packets produced 128 accepted frames, channel 9, 20 MHz,
  64 subcarriers. The first-to-last receive interval was approximately 12.61 s.
- Every recorded I/Q component, host timestamp, channel, bandwidth and RSSI
  matched its collector input exactly.
- Recording the same collector JSONL through the file adapter produced identical
  replayed frames to the live UDP capture.
- Inspect, replay, events, calibration and RF-memory export completed. The
  pipeline produced 5 events and 10 memory records; these are processing
  observations, not independently verified physical detections.
- 87 non-CSI/other datagrams were excluded by the bounded collector.
- Full Windows workspace tests, clippy with warnings denied, and rustfmt passed.
- The optimized Windows CLI reproduced the debug build's replay, events,
  calibration and RF-memory output exactly for this capture. The locally built
  Windows Node addon also inspected and replayed all 128 frames and produced
  the same 5 events. This does not add Windows binaries to the Linux-only npm
  publication workflow.

Serial output on this firmware contains boot/status text. Direct JSON serial was
not qualified. Linux pseudo-terminal tests cover serial transport mechanically;
they do not substitute for physical serial validation. No ESP32-S3, other
firmware version, or multi-antenna packet qualification is claimed.

## Reproduce

Configure the device separately to stream ADR-018 raw CSI to the chosen local
interface. Stop any competing receiver. Build the CLI, then run:

```sh
cargo build --release -p rvcsi-cli --locked
python scripts/verify_esp32_udp_hardware.py \
  --binary /absolute/path/to/rvcsi \
  --bind HOST_LAN_IPV4 --device ESP32_LAN_IPV4 --port 5005 --node NODE_ID \
  --frames 128 --seconds 45 --output /private/new/evidence-directory
```

Use `rvcsi.exe` on Windows. Supply actual interface/device addresses and the
configured node ID. The output directory must be new and outside the checkout.
The script neither configures nor flashes hardware. UDP source-IP filtering is
not authentication; run this on a trusted network. The script saves raw RF data,
collector records, captures and derived output **locally**. Do not commit them.
